ReadyUp

Pre-deployment checks, written in TypeScript and run from the command line.

rdy run

ReadyUp is a command-line tool. A project writes its pre-deployment checks in TypeScript, groups them into a kit, and runs them with rdy run before a deploy, on a laptop or in CI. The next five minutes: why it exists, what a check looks like, what a run does when a check fails, and how to start.

Most teams already have deploy checks. They live in a wiki page, in a channel thread, and in whoever deployed last time. The code moves and the list does not. Nobody runs the list the same way twice, and the thing it was meant to catch shows up after the deploy, when it is expensive to fix. That is the gap.

One file of checks, one command

A kit is a file of checklists; rdy run runs them and prints what to fix

The idea is small. A kit is a file. It exports checklists, and a checklist contains checks. One command, rdy run, runs them and prints one line per check: a pass, or a failure with the reason and a fix hint that the kit author wrote. The exit code says whether the run passed, so the same command works in a terminal and in a pipeline.

Writing a check

for kit authors

.readyup/kits/preflight.ts
A preflight kit, run before a smoke test. A check is a few fields. The name states what must be true. The check is the function that rdy runs; it returns true, or false with a detail. The fix is what prints when the check fails. Severity decides whether a failure fails the run: error does, warn is reported and does not. Everything else is structure: the checklist, and the helpers that the kit imports.

Preflight

before a command: the kit from the last slide

rdy run && pnpm smoke
Compile the kit and run it: one line per check, the count line, the verdict naming the threshold, and the exit code that gates the smoke test. Step through it, then change the environment in the panel. Stop Docker: the check fails at error, the fix prints, the run fails with exit one. Take the API down instead: that check fails at warn, so it is reported with its fix, but the run passes. The severity decides the verdict, not the check. The JSON tab is the same run for a machine.

A run, step by step

The deploy checklist: six checks, three of them nested

package.json exists passes, so the check under it runs

build output present fails at error: dist/index.js not found

Under the failed check, two checks do not run and are reported as blocked

Each result counts once in the total

The same run, as rdy prints it

Here is a kit with nesting. package.json exists passes, so the check under it runs. build output present fails, and its severity is error. Its two children never run: they are reported as blocked, because their parent failed. NODE_ENV is set fails too, but at warn. base image is pinned does not apply here, so it is skipped. Each result counts once in the total: one error, one warning, one passed, two blocked, one skipped. Then the verdict. This run fails on error. The error fails it; the warning alone would have left it passing, with exit code zero. Exit code one is what CI acts on. And this is what rdy printed for the same run: the same tree, the fixes, the total, the verdict.

The same run, for a machine

for CI owners and agents

rdy run --json

One document on stdout; --detail summary keeps the failures and fixes alone

The same run with dash dash json. One JSON document on stdout, every human line on stderr. The verdict is a boolean, the counts are the same six tallies, and every failed check carries its detail and its fix. Dash dash detail summary drops the passes and keeps the failures and fixes, which is the shape an agent wants before it goes and fixes them. The schema ships inside the package.

What a kit is for

four questions, one mechanism

Preflightbefore a command

Is the environment ready for the deploy, the smoke test, the release?

preflight · rdy run && pnpm smoke

Driftagainst a template

Do the workflows and configs still match the templates that the installed package ships?

release-kit · rdy run --from npm:@williamthorsen/release-kit

Adoptionand migration

Where does the code still hand-roll what a package it already installed provides?

toolbelt.errors · rdy run --sources

Onboardinga machine or a person

Is this machine still set up the way the bootstrap left it: tools, links, worktrees?

machine · rdy run machine

A kit asks one question; the same command answers all four

Four kinds of kit people actually write. Preflight, before a command that needs the environment ready. Drift, from a package that ships its own templates and checks that the repo still matches them. Adoption, where a package reports the places that still hand-roll what it provides. Onboarding, where a machine checks itself against the state the bootstrap left. Same command, same output, same exit code.

Drift

against a template: the kit ships with the package

rdy run --from npm:@williamthorsen/release-kit
release-kit ships its workflows as templates, and it ships a kit that checks the repo still matches them. Nothing to write: the kit comes with the package. Let a workflow drift from its template and the kit says which one and how to regenerate it. Remove a workflow and the check under it is blocked rather than failed: it never ran.

Adoption

using what is installed: a real run from this repo

rdy run --from npm:@williamthorsen/toolbelt.errors
The errors package ships a kit that sweeps the consumer's sources for the idioms it replaces. Each check reports a fraction: sites examined, of sites in scope. One site still narrows a thrown value by hand, named by file and line, with the fix. It is a recommendation, so the run passes. That is adoption: the package tells you where you are not using it yet.

Onboarding

a machine checks itself: two checklists, one summary

rdy run machine
A machine kit: is this Mac still in the state the bootstrap left it? Two checklists, tools and install, each with its own total, then a summary. The live worktree check has two checks under it; take the worktree away and both are blocked. A stray setting in gitconfig is a warning with a fix. The run passes until a tool is missing.

Gating a pipeline, trusting a shared kit

for CI owners

The exit code is the gate

rdy run
  • exit 0Ran and found no problems
  • exit 1Ran and found problems fix the repo
  • exit 2Could not complete the invocation fix the invocation

A kit that another team publishes

publisher

rdy compilebundles the kit

git committhe bundle and its manifest, in the repo or the package's files

rdy verify --rebuildin CI: fails on a bundle that no longer reproduces from its source

consumer

rdy run --from npm:@acme/eslint-configthe kit published with the installed version

rdy run --from github:acme/ops@v2the kit committed at that ref

One exit code gates the pipeline; a published kit runs at the version the project has

Two questions for a CI owner. Gating: the exit code is the contract. Zero, no problems. One, fix the repo. Two, fix the invocation. Trust: a team publishes a kit as the compiled bundle and its manifest, committed to the repo or listed in its package's files, and runs verify with rebuild in CI, which fails if the bundle no longer reproduces from its source. Consumers run it from the package they already install, or from the repository at a pinned ref.

Get started

Node 24 or later
  1. pnpm add --save-dev readyup esbuild esbuild compiles the kits
  2. rdy init writes .config/readyup.config.ts and the starter kit .readyup/kits/default.ts
  3. rdy compile bundles the kit
  4. rdy run runs it, locally or in CI

npmjs.com/package/readyup rdy help lists the doc topics in the terminal

To start: add readyup and esbuild as dev dependencies, on Node 24 or later. rdy init writes the config and the starter kit from earlier. rdy compile bundles it, and rdy run runs it, the same way locally and in CI. The docs are on npm and in the terminal: rdy help lists the topics. Questions?
